# GitLab MR Review

Review GitLab merge requests with a senior-engineering lens. This skill covers the **mechanics** of getting the diff and doing targeted deep-dives. For the actual review **criteria** (correctness, security, simplicity, surgical changes), load `pr-review` alongside this one.

## Workflow

### 0. Tool Choice — user preference: read via git/MCP, never throwaway Python scripts

User explicitly rejected Python-script reads during MR review ("Ủa sao giờ bạn toàn tạo file python để thực thi không nhỉ, sao không call mcp hoặc glab cli cho nhanh?"). Hierarchy:

| Operation | Tool | Why |
|---|---|---|
| READ file contents / diffs / greps | `git fetch origin <branch> develop` then `git show origin/<branch>:<path>` / `git diff origin/develop...origin/<branch>` / `git grep` | cheapest + most accurate (direct ref, no API mapping, no token cost) |
| READ MR metadata (title, desc, diff_refs, head_sha, state) | MCP `get_merge_request` | structured single call; git can't see MR metadata |
| READ full file substantially in context | MCP `get_file_contents(ref=<branch>)` | for files you'll reason over inline |
| WRITE (threads, notes, approve, merge, issues) | MCP tools | schema-checked, position-anchored threads |
| WRITE fallback | Python REST script (`GITLAB_TOKEN`, `/api/v4`) | only when MCP errors ('Extra data' with long/Vietnamese bodies) |

Do NOT write throwaway Python scripts into /tmp for READING MR data (metadata, changed files, diffs, notes, locale parity) — one `git fetch` + `git show`/`git diff` covers ~90% of read needs at near-zero cost, MCP covers the rest. Reserve scripts for: (a) MCP write failures, (b) genuine multi-step logic loops that filter/aggregate before printing. (Same preference stored in memory 2026-08.)

### 1. Get MR Metadata

Use GitLab MCP tools on the project (project_id from the MR URL, e.g. `vppos-team/erp-admin`):

```
mcp__gitlab__get_merge_request(project_id, merge_request_iid=NNN)
  → title, description, source_branch, changes_count, approval status
mcp__gitlab__list_merge_request_changed_files(project_id, merge_request_iid=NNN)
  → list of all changed file paths
```

**User pastes an ISSUE URL when asking to review "MR này"** — `/-/work_items/NNN` is an issue, not the MR. Fetch the issue (`get_issue`), then locate the open MR via `list_merge_requests(project_id, state='opened')`, matching by title keyword or the issue reference in the description (real case: work item #133 → MR !539 `feat(product): align product catalog...`).

**Reverse direction — MR cites an issue (`Issue / Ticket: #N`)**: fetch the issue too, BEFORE reading the diff. Spec-driven issues carry the BE contract + acceptance criteria that double as the review checklist (see §9 'Spec-driven MRs').

### 2. Get the Full Diff

```
mcp__gitlab__get_merge_request_diffs(project_id, merge_request_iid=NNN)
  → diffs array with old_path, new_path, and diff hunks
```

Read the description in the MR to understand intent before diving into code.

### 3. Read Files from the MR Branch (for deeper review)

Use GitLab MCP to read the **full file** from the branch — **never** from a local checkout of a DIFFERENT branch (local `develop`/`main` may not match the branch, leading to false review claims).

> **User preference — deep review = local branch checkout.** When the user asks to "checkout nhánh ... pull mới nhất rồi đọc local để review kĩ" (or the MR needs a multi-file convention survey), do: `git fetch origin <source-branch>` → `git checkout <source-branch>` → `git pull` → **verify `git rev-parse HEAD` == MR `head_sha`** → read files locally (faster, full file-tree + grep access). This is safe because the checked-out branch IS the MR state — the "never local" rule targets reading a stale/different branch. Keep MCP `get_file_contents` for quick single-file claims from the MR ref.

```bash
mcp__gitlab__get_file_contents(project_id, file_path="path/to/file.ts", ref="<source-branch>")
```

For each changed file, read the **full file** (not just the diff) with the branch's content —
diffs alone don't show surrounding context like imports still used elsewhere,
other functions in the same file, etc.

### 4. Read Changed Files Systematically

For each changed file:

- Read the **full file** (not just the diff) — the diff doesn't show surrounding context like imports still used elsewhere, other functions in the same file, etc.
- Check **unused imports**: if the diff removes an old import and adds a new one, verify the old imports are truly unused in the rest of the file.
- Check **prop/interface changes**: if the diff adds new props, verify callers pass them (or they're optional).

### 5. Blast-Radius Check for UI Component Migrations

When the MR replaces raw UI components (Popover, DropdownMenu, raw Button) with a shared component (TableOptionMenu, etc.):

- **Read the shared component's source** in the UI library package (e.g. `packages/ui/src/components/customs/` or `components/shared/`).
- Verify the shared component handles:
  - **Separators**: old code may have had `border-b` between items — check if the new component has it built in.
  - **Hidden/filtering**: old code may use conditional rendering (`&&`) or explicit `hidden` — check the new component's API.
  - **Empty state**: what renders when no items are visible?
  - **Alignment/offsets**: verify default `align`, `sideOffset`, `collisionPadding` match the old behavior.
  - **Trigger icon**: does the new component use the same icon as before?
- Use `search_files` to find **all existing consumers** of the new component to understand established patterns.
- **Branch-aware blast radius — which branch of the component does each consumer hit?** A Field-style wrapper renders DIFFERENT JSX per branch: `name` present → FormField branch; no `name` → bare render branch; `mode='view'` → read-only branch. A change to one branch only affects consumers on THAT branch — classify every consumer by the branch-selecting props (`name`, `mode`), not by import presence alone. Real case (MR !550): the `!name` branch started rendering `Label` + required `*` → only `ProductCreateDialog` (no `name`) gained labels — an improvement (labels were previously missing), not a regression, but still must be disclosed + visually verified per the issue AC "không ảnh hưởng ngoài ý muốn tới các màn khác"; HR dialogs + sale's `CustomerSearchInput` pass `name` → FormField branch, untouched; the `mode='view'` restyle only hit the MR's own dialog.
- **Similar-name sibling component trap**: `CreatableAsyncOptionsComboboxField` vs `AsyncOptionsComboboxField` vs `AsyncPaginatedCombobox` — a repo-wide grep for `mode="view"` (or a prefix of the changed component) matches the SIBLING component too (real case MR !550: HR ScopeSection's `mode="view"` hits were `AsyncOptionsComboboxField`, NOT the changed component → false blast-radius scare). Verify the exact component identifier in each matched line before flagging other screens.
- **View-mode className is dead code**: if a component's view branch hardcodes its own styles (`<Input className="bg-surface-subtle h-10!..." />`), caller-passed `className` is IGNORED in view mode → a caller ternary with a readOnly half (`readOnly ? 'bg-x!' : 'bg-y!'`) has a dead branch; flag 🟢 (drop the dead branch or accept slight color drift).
- **MR title under-describes scope**: count the MR's user-visible changes vs the title (real case MR !550: title "limit dropdown height" but the MR also aligned field heights + relocated tax-rate creation into the combobox create-flow via `renderCreateDialog`). A title naming only one of several changes misleads release notes/audit — require title + How section to name every behavioral change (this also catches "fix" titles hiding feature moves).

### 6. Convention Alignment Check (AGENTS.md + DTO)

When an MR changes established patterns — especially migrating from mock to real API, restructuring feature files, or adding new endpoints — verify it aligns with the monorepo's documented conventions in AGENTS.md files and shared types.

**Dimensions to check** (load the root `AGENTS.md` + app-level `AGENTS.md` first):

| Dimension | What to Verify |
|---|---|
| **AGENTS.md compliance** | DTO-first display, i18n flatten (`entity.fieldName`), mutation+toast, 4 UI states, no adapters/mappers |
| **API layer separation** | Dumb HTTP in `apis/`, React Query in `hooks/`, no `useQuery`/`useMutation` in `apis/` |
| **API response envelope** | Response typed as `ApiResponse<T>` from `@hilo/shared` with T = item\|item[] (`data` IS the payload: array for list, item for detail); NO wrapper interface around `ApiResponse` (e.g. all-optional `CrmPagedListResponse`); NO normalize/resolve helpers for BE response shapes (`normalizePagedItems`, `resolvePagination`); pagination read from `meta.pagination` (`page`/`totalPages`/`pageSize`/`totalItems`), not from payload — see `docs/solutions/conventions/2026-08-05-api-response-envelope-contract.md` |
| **DTO alignment with shared types** | Compare feature-local DTOs against `packages/shared/src/types/*.types.ts` field-by-field |
| **DTO drift assessment** | ✅ Aligned / ⚠️ Minor drift (different field name, same semantics) / 🔴 Major drift (different enums, types) |
| **URL state pattern** | Uses `createSharedListUrlStateSchema` + `useUrlState` from `@hilo/shared`, not manual URL parsing |
| **Shared infrastructure reuse** | Uses existing `@hilo/shared` (apiClient, PATHS, formatDate, getApiErrorDisplayMessage, etc.) and `@hilo/ui` (DataTable, Button, etc.) before creating new |
| **4 UI states** | Loading (Skeleton/Spinner), Error (Retry button with `refetch`), Empty (message/CTA), Success |
| **Mock removal completeness** | Old mock files deleted, no `use{Feature}DataSource` pattern remaining, `apis/` folder exists |
| **Feature structure** | Has `apis/`, `components/`, `constants/`, `hooks/`, `types/`, `index.ts` (FSD public boundary) |

**Workflow:**

1. **Read the AGENTS.md hierarchy** — root → app → feature. Load root AGENTS.md first, then the nearest app/feature AGENTS.md.

2. **Read `docs/solutions/`** — check if a prior analysis of the same module already exists (e.g., a migration plan) and verify the MR implements it.

   > **Pattern-deprecation cross-check (real case, MR !514):** `docs/solutions/architecture-patterns/` can supersede a pattern that `apps/*/AGENTS.md` still documents as canonical — e.g. the `use*DataSource` + `DataSourceResult<TRow>` pattern was deprecated on 2026-07-27 in favor of the 3-Layer list wiring, but `apps/hr/AGENTS.md` was not updated and still lists DataSource as canonical. Reading only the AGENTS.md hierarchy misleads you into accepting deprecated code (or wrongly rejecting 3-layer code). **Always scan `docs/solutions/architecture-patterns/` for the newest pattern before scoring list-wiring/DataSource compliance.** See `references/convention-survey-dimensions.md` Dimension 7 for the full DataSource vs 3-Layer rubric and the shared `computeTotalPages`/`safePage` pagination-util rule.

3. **Identify a reference implementation** — find an existing feature that already uses real APIs in the same app or sibling app (e.g., HR Salary Fund Management for ERP finance MFEs). Compare the MR's patterns against it.

4. **Cross-reference DTOs field-by-field** against `packages/shared/src/types/`. When the MR intentionally drifts from shared types (because the shared types are outdated), note it explicitly in the review.

5. **Produce a structured comparison table** showing MR pattern vs reference vs convention:

   ```
   | Aspect | HR Reference | MR Pattern | Match? |
   |---|---|---|---|
   | API layer | `apis/{name}.ts` | `apis/{name}.ts` | ✅ |
   | Query keys | `QUERY_KEYS` in hooks | `QUERY_KEYS` in hooks | ✅ |
   | List query | `useQuery` + `enabled: !!user` | `useQuery` + `enabled: !!user` | ✅ |
   ```

6. **Score each dimension** as ✅ Excellent / ⚠️ Needs Discussion / 🔴 Issue. Include in the review summary.

> **Reference file:** `references/convention-survey-dimensions.md` — full dimension definitions, common drift patterns, and reporting templates for convention alignment surveys.

### 6b. Efficient Diffing for Large MRs

For MRs touching many files (90+), pulling the whole MR diff or reading each full file is slow and floods context. Two high-leverage shortcuts:

- **Targeted per-file diffs**: `mcp__gitlab__get_merge_request_file_diff(project_id, merge_request_iid, file_paths=[...], unidiff=true)` — batch the files you actually need to assess a dimension (e.g. all `*DataSource.ts` hooks) and read only their hunks, not the whole MR diff.
- **i18n parity via diff, not read**: locale files (`packages/locales/src/translations/{en,vi}/...json`) can be 300KB. Get the diff for **both** the `en` and `vi` file in one call and compare the added/removed hunks side-by-side — every key the MR adds must appear in both. Never read the full locale file just to confirm parity.
- **Huge persisted diffs → parse with `execute_code`, don't `read_file`**: `get_merge_request_diffs` on a 90+ file MR returns ~160KB and gets persisted to `/tmp/hermes-results/*.txt` as a **single escaped JSON line** — `read_file` on it gives one 160KB line (useless) and counting `+`/`-` lines is misleading. Instead, in `execute_code`: `json.loads` the file, then `json.loads(data['result'])` (the inner string is itself JSON), giving an array of `{new_path, diff}`. Print a per-file index (`len(diff)` chars) first to see the size distribution, then print the actual `diff` hunks for the high-value files by index. This keeps context small and lets you triage which files deserve full reads.
- **Nested i18n JSON cannot be dotted-grepped**: keys like `t('features.attendance.filters.searchPlaceholder')` resolve through NESTED objects (`"features":{"attendance":{"filters":{...}}}`), so `grep 'features.attendance.filters'` returns 0 even when the key exists. To verify a referenced key actually exists, load the locale file and traverse the nested dict in `execute_code`, checking BOTH `en` and `vi`. Grepping the dotted path produces false "missing" results.
- **Cheapest verification: local `git fetch` + `git show origin/<branch>:file | grep`** — for targeted claim checks (does key X exist? does field Y exist in the mock? does the child component destructure prop Z?), fetching the branch into the local clone beats `get_file_contents` (full-file reads on 60–80KB locale JSONs) by an order of magnitude in tokens:
  ```bash
  git fetch origin <source-branch>     # ALWAYS fetch fresh — never grep the working tree
  git fetch origin develop             # develop moves constantly; MRs silently flip to "conflict"
  git rev-parse origin/<source-branch> # TRAP: after fetching MULTIPLE refs, FETCH_HEAD = the LAST one fetched (develop), NOT the MR branch. Always address refs by name, never FETCH_HEAD, in multi-fetch sessions.
  git show origin/<source-branch>:path/to/file | grep -n 'pattern'      # exact-key/field existence
  git show origin/<source-branch>:path | grep -c '"exact.key"'          # count occurrences (0 = missing)
  git diff origin/develop...origin/<source-branch> -- path/to/file | head -80  # per-file diff vs merge-base
  ```
  Repo locations (erp-admin): main clone `~/Projects/Hilo-Vppos/erp-admin`; the user's dedicated REVIEW worktree is `~/Projects/Hilo-Vppos/erp-admin-review` (gitdir → `erp-admin/.git/worktrees/erp-admin-issue-60`; remote branches are NOT checked out — fetch first: `git fetch origin <source-branch> develop`). `~/Projects/Hilo-Vppos/Documents/ERP` is NOT a git repo — don't cd there.

  **Worktree working-tree trap (real case, MR !539):** the review worktree's WORKING TREE sits on its own branch (currently `review`) — `read_file`/`search_files`/`grep` on it return THAT branch's content, which can match NEITHER develop NOR the MR branch (MR !539: working-tree `useProductCatalogQuery.ts` was a 19-line file existing on no relevant branch, while both develop and the MR branch carried the full 134-line version; reading it produced a false "develop refactored, MR will conflict" scare that the diff immediately disproved). For review reads, ALWAYS `git show origin/<source-branch>:<path>`; verify `git rev-parse origin/<source-branch>` == MR `head_sha` first.
  This settled every disputed claim in the MR !514 review (7 missing i18n keys, mock lacking `createdAt`, dead toolbar props, leaveDays regression) in a handful of commands. Use MCP `get_file_contents` only for files you need to read substantially in context. Caveat: a stale local `origin/develop` makes `...` diffs misleading — always `git fetch origin develop` first in the same session.

### 7. i18n Consistency Check

When the MR touches locale files:

- Verify **both language files** (`en/` and `vi/`) have matching keys added **and** removed together.
- Check that toast success/error message keys exist for every new mutation.
- Confirm action label keys (deactivate/reactivate, etc.) follow the project's naming convention.
- If an entity already has existing i18n keys for similar actions, the new keys should follow the same pattern.

**Automate the existence check** — `scripts/verify_i18n_keys.py <head_sha> <feature-dir>…` regex-extracts every `t('...')` key from the changed files, traverses BOTH en and vi locale JSON (nested-dict, so no dotted-grep false negatives), and reports missing keys with exit code 1. Namespace-agnostic: checks finance.json AND common.json. Verified on MR !527 (~200 keys, clean) — the same check that would have caught MR !514's 7 missing placeholder keys in one run. ns-prefixed keys (`t('sale:customer.messages.validation.x')` in zod schemas) are stripped before lookup (fixed MR !549 — they used to false-positive as missing even when present in sale.json; with `--ns=<x>` an explicit prefix naming a DIFFERENT ns is still a miss).

**Enum-value key casing — this repo's convention is LOWERCASE** (`customer.status.active`, `customer.customerType.enterprise` — generated with `value.toLowerCase()`), even when an issue AC asks for uppercase (issue #137 originally specified `customer.{field}.{VALUE}` uppercase; the user overrode to lowercase 2026-08: "tôi yêu cầu lowercase trong files i18n"). When an MR's enum keys deviate from the AC's stated casing, don't auto-flag 🔴 — surface as a decision for the user; the AC text may need updating, not the code. Related: the MR description claim "không đổi hành vi" must be amended when the option set actually narrowed (see §9 enum-narrowing entry).

**Enable-`showToolbar` ⇒ every new placeholder key must exist in BOTH `en` and `vi`** (real incident, MR !514): an MR flipped many `DataTable`s from `showToolbar={false}` to `showToolbar` and passed `searchPlaceholder={t('features.X.filters.searchPlaceholder')}`. The MR added keys only for 3 features; 7 referenced keys (`features.{attendance, changeManagement, organizationConfig, workRequestConfig, workScheduleConfig, insuranceTax}.filters.searchPlaceholder`, `features.attendance.timesheet.searchPlaceholder`) were missing from both locale files → placeholders render the raw key string. **Don't just diff what the MR added — enumerate every `t('...')` key the components now reference and verify each exists in `en` AND `vi`** (traverse the nested JSON; dotted grep is unreliable, see §6b). Missing placeholder keys are 🔴 because they're user-visible.

**Partial-fix trap + diff-context trap (real case, MR !514 re-review):** a commit named `fix(hr): restore missing search placeholder translations` added only **2 of the 7** flagged keys (its diff had just 2 hunks per locale file); 1 key (`features.attendance.filters.searchPlaceholder`) remained missing while 5 components still called `t()` on it. Two traps:
- **Don't infer coverage from commit message or hunk count** — a "restore missing translations" / "address review feedback" commit can be partial. Enumerate EVERY flagged key independently against branch state, don't just spot-check what the commit touched.
- **Diff-hunk context ≠ key presence** — the fix's hunk showed `searchPlaceholder` in *context* lines right next to the added `timesheet` block, which looks like the key exists. But the checked namespace (`features.attendance.filters`) existed with only unrelated keys (`allEmployees`, `allDepartments`, `allStatuses`) — the parent namespace existed, the key did not.
Authoritative re-verify (both halves): (1) `git grep -n "searchPlaceholder" FETCH_HEAD -- apps/hr/src/features/...` to enumerate every component reference to the key; (2) traverse the nested JSON in BOTH `en` and `vi` for each referenced dotted key. Existence of a parent namespace object ≠ existence of the key inside it; if a lookup returns `None`, dump the subtree (`find all searchPlaceholder keys + list parent-namespace keys`) before concluding — cheap and kills ambiguity.

**Component-side key RENAME without locale update — the reverse-direction trap** (real case, MR 512 round 5): a 🟡 flagged 3 surface-nested keys for one field (`productCatalog.createModal.priceAfterTax` / `table.priceAfterTax` / `detailModal.priceHistory.priceAfterTax`) and asked to flatten to ONE key `productCatalog.priceAfterTax`. The follow-up commit `refactor(product): remove redundant product catalog request helpers` renamed ALL components to `t('productCatalog.priceAfterTax')` (+ `priceAfterTaxValue`) — but **never added the flat key to `en`/`vi` `common.json`**. Old nested keys stayed in the JSON with 0 consumers (dead), while the referenced flat key is missing → i18next (no `missingKeyHandler`/`returnNull` in `packages/locales/src/i18n.ts`) renders the raw key string `productCatalog.priceAfterTax` in table header, dialog labels, detail modal — a 🔴 user-visible regression, WORSE than the original 🟡 (the key existed nested before; now it doesn't exist at all). Two traps:
- **Substring grep lies in BOTH directions**: `git grep 'priceAfterTax' <branch> -- packages/locales` shows hits (the dead nested keys) and looks like the key exists. Verify the EXACT dotted path at the namespace's top level — JSON-traverse `productCatalog.priceAfterTax` (`pc.get('priceAfterTax')` → `None` via python json module) — never count substring hits.
- **i18n flatten/rename fixes have TWO mandatory halves**: (1) rename the `t()` calls in components, AND (2) add the new key at its new path in BOTH `en` + `vi` in the SAME commit (optionally remove the now-dead old keys). When re-verifying an i18n-refactor commit, check all three: new key exists in en+vi at exact path; old keys have 0 consumers (`git grep -n -E "createModal\\.priceAfterTax|table\\.priceAfterTax" <branch> -- apps/` → empty); no component still references the old path. Do NOT approve a MR that flipped components to a nonexistent key — the fix commit itself introduced the regression.

**Provenance check for out-of-scope locale changes** (real incident, MR 512): a vi-only rename of navigation keys (`salary` → `salary_fund_management`/`salary_management`) was buried in a product MR. To attribute and prove impact before flagging:
1. Compare `en` vs `vi` on the branch — a vi-only change is a parity violation.
2. Read the same section on `develop` — if develop still has the old key, the MR overwrites it on merge.
3. Read the pre-merge branch tip (`get_file_contents(ref=<old commit sha>)`) — tells you which commit introduced it (feature commit vs merge-conflict resolution).
4. Find code consumers of the key (e.g. `APP_MODULES` `nameKey` in `packages/shared/src/config/navigation.ts`) — a key removed from vi but still referenced renders as the raw key string in the UI. That makes it 🔴, not a nitpick.

**Verify namespace-prefix claims before flagging**: a key like `common:productCatalog.title` is NOT a "double namespace" bug. i18next's `nsSeparator: ':'` makes `ns:key` resolve the namespace explicitly; with `defaultNS` already `common`, the prefix is redundant but works. Confirm by reading the consuming hook (e.g. `useTranslation()` with no ns arg in `usePageMetadata`) and the i18n init config (`defaultNS`). Demanding a fix without reading the implementation produces false positives that erode review trust (real incident: MR 512 re-review had to retract this exact 🔴).

**Reverse direction — dead keys**: every key the MR ADDS should be referenced somewhere (`git grep -n '<key-part>' origin/<branch> -- apps/`). Unreferenced added keys (real case MR !514: `features.attendance.tabs.timesheet.searchPlaceholder` existed in en+vi while components use `features.attendance.timesheet.searchPlaceholder`) are 🟢 nitpicks — they bloat locale files and mislead future key searches. Check this only after the existence direction passes. **Consumer-count recipe + substring trap** (real case MR !547): enumerate mechanically — `for k in <added-keys>; do git grep -c "$k" <branch> -- apps/ packages/ | grep -v translations | wc -l; done` — but substring hits LIE in the consumer direction too: `deleteConfirm` matched `deleteConfirmTitle`/`deleteConfirmDescription` in OTHER features (documents tab, attendance dialogs), and `deleteError` matched 4 unrelated sibling features — verify each hit is the EXACT dotted key (`t('features.employee.deleteConfirm')`) or review hits individually before declaring "has consumer". Two distinct dead-key findings surfaced: (a) MR **edits a pre-existing dead key** (`deleteDescription` text rewritten while 0 consumers on develop AND branch — the new dialog uses `deleteDescriptionBeforeName/AfterName`) → pointless edit, 🟢 cleanup of all dead siblings (`deleteConfirm`, `deleteError`); (b) MR **adds a whole intended-but-unwired block** (`deleteConsequences.*` 5 keys matching issue AC "nêu rõ hệ quả" but never rendered — prose covers only 3 of 5 consequences) → 🟡: render the block (the keys prove intent) or drop it; cross-check the issue's AC text to judge which.

**Cleanup commits that REMOVE dead keys can over-delete — re-verify referenced keys survive** (real case MR !547 round 3): the fix commit removed 12 keys (5 `deleteConsequences.*` + 4 restore + 3 old `deleteConfirm`/`deleteDescription`/`deleteError`) from en+vi in one hunk each. A removal is correct only when ALL THREE hold: (1) every removed key had 0 exact consumers (`git grep -n "t('features.employee.deleteX')" <branch> -- apps/ packages/ | grep -v translations` → empty; substring hits don't count); (2) every key components STILL reference exists in BOTH en+vi after the deletion (JSON-traverse the exact dotted paths — a cleanup hunk can look innocent and still kill a used key); (3) the new spec actually exercises the flow the review asked for (dialog test should cover render, confirm-once, cancel, loading-disabled). The "-14-line locale hunk + 149-line new spec" shape = the classic dead-key cleanup + dialog-test fix; verify both halves independently, then re-run the focused specs + `tsc -p tsconfig.app.json` at the new head before declaring "fix đúng".

**Namespace-aware verification — check the component's ns BEFORE flagging** (real case, self-MR #120 review): a `t('features.attendance.timesheet.*')` key can be "missing" from `common.json` yet resolve fine because the component calls `useTranslations('hr')`. Conversely `employeeForm.fields.joinDate` (new field label in 3 JobInfoTabs) was genuinely missing because those components call `useTranslations('common')`. Protocol: (1) read each changed component's `useTranslations('<ns>')` argument — files can mix namespaces (`t` from 'common' + `tShell` from 'shell'); (2) JSON-traverse THAT namespace file in BOTH en and vi, not just `common.json`. For NEW keys introduced by the MR, enumerate mechanically — `git diff <base>...HEAD -- apps packages | grep '^\+.*t(' | sort -u` — then check each. Sibling-key heuristic: if sibling keys (e.g. `employeeForm.fields.probationDate`) exist but the new field's key doesn't, it's a real 🔴 (raw key renders in UI). Note: a semantically-identical key with a DIFFERENT name (dead `entryDate` vs field `joinDate`) does NOT satisfy the convention — key must follow the field name (`{entity}.{fieldName}`), add the missing key, don't reuse the dead one.

**Two-arg `t(key, default)` fallback — the silent wrong-language trap + script blind spot** (real case, MR !529): `t('dashboard.filters.panelTitle', 'Bộ lọc')` — i18next's defaultValue as 2nd arg renders the literal (Vietnamese) fallback when the key is missing, so the UI shows WRONG-LANGUAGE text instead of a raw key string — AND `verify_i18n_keys.py`'s regex only matches the single-arg form, so 12 missing `dashboard.filters.*` keys (en+vi) slipped past the script in MR !529 (panelTitle, searchLabel, statusLabel, sortLabel, dateTypeLabel, dateType, dateTypeApplied, dateTypeSubmitted, clearFilters, emptyOptions, multiSelectPlaceholder, multiSelectSearchPlaceholder — only searchPlaceholder/status/sort/dateTypeAll/reset existed). Protocol: (1) enumerate two-arg forms in changed files: `git show <head>:<file> | grep -oE "t\('[^']+',\s*'[^']*'\)"`; (2) JSON-traverse BOTH en+vi for each key; (3) flag missing ones 🟡-🔴 (en users see Vietnamese) and require adding keys + dropping the literal fallbacks. Second trap: **run the verify script with CHANGED FILES ONLY** (`git diff --name-only <base>...<head> | grep -E '\.(ts|tsx)$' | grep -v locales`, pass those paths) — scanning whole feature dirs pulls test fixtures and PDF strings ('%PDF-1.4', 'Engineer', 'a@vppos.vn') that drown the real missing keys. Third form — **object-form two-arg `t('key', { defaultValue: '...' })`** (real case, MR !531): i18next also takes an options object; the script misses these too (`directory.toolbar.clearSearch` referenced with `{ defaultValue: 'Xóa tìm kiếm' }` was missing from both en+vi and only caught by a manual object-form `re.findall`). Enumerate all three forms: single-arg, string-literal two-arg, AND object-form.

**2-arg false positive — pre-existing keys on develop are NOT MR findings** (real case, MR !540): `verify_i18n_keys.py` reported 3 two-arg keys missing (`features.employee.activeSuccess`, `inactiveSuccess`, `table.rows`) while the MR never touched them — they were pre-existing on develop, only *referenced from* files the MR modified. The script scans whole changed files, not MR-introduced lines. Before flagging any script-reported missing key: `git grep -n '<key>' origin/develop -- apps/` — if the usage exists identically on develop, it's pre-existing, downgrade to informational (or drop). Only flag keys the MR newly references or removes.

**Key added at the WRONG namespace level — dead key + missing referenced path in one commit** (real case, MR !531): the author added a `filters` block under `features.directory.filters` in `employee.json` (en+vi) while `DirectoryHeaderToolbar.tsx` (namespace `employee`) references **top-level** `directory.filters.*` → all 10 referenced keys missing (raw-key UI in the panel title/labels/buttons) AND the added path has 0 consumers (dead). Detection: a key "exists" only at the EXACT dotted path the component references — `t('directory.filters.X')` ≠ `features.directory.filters.X`. JSON-traverse the exact referenced path; if missing, dump BOTH the top-level object keys and the `features.*` subtree to see where the author actually put the block. Same family as the rename trap but the key was NEVER at the right path. 🔴.

**Wrong-path key addition — added key with 0 consumers while the real missing key stays missing** (real case, MR !531): MR added `features.employee.import.actions.settings` to `hr.json` (en+vi) with **zero consumers** (`ImportEmployeeDialog` only uses `cancel/processing/import`) while the actually-referenced `features.employee.actions.settings` (`apps/hr/.../EmployeeHeader.tsx`) was STILL missing in both languages → raw key renders in the settings icon tooltip, and the fix was ineffective + out-of-scope (employee-MFE MR touching an HR import-dialog locale). Detection: (1) for every ADDED locale key, `git grep -n '<key>' <branch> -- apps packages | grep -v translations` — 0 hits = dead; (2) when a "settings"-style key is missing and the MR added a near-identical one elsewhere, diff the paths (`import.actions.settings` vs `actions.settings`) — the author likely placed it in the wrong subtree. Flag as 🟡-🔴: the intent to fix is visible but the actual user-visible key is still broken.

### 9. Proven High-Yield Checks

Checks that repeatedly find real 🔴/🟡 in this codebase's MRs:

- **Edit-form round-trip (data loss)** — every field a create/edit dialog submits must round-trip from the source DTO. A form initializer that hardcodes defaults on edit (`duration: '12'`, `quantity: ''`) silently overwrites real backend values (`durationDays`, `totalQuota`) on save — editing a product's name can wipe its quota. Check the DTO carries every field the dialog can clobber, and the edit initializer reads from the entity.
- **Wrapper response interface + response-shape normalization helpers = 🔴 contract evasion** (real case, MR !539) — a feature types list responses as a feature-local all-optional wrapper (`CrmPagedListResponse<T>` with `items?/data?/total?/page?/pageSize?/pagination?`) instead of `ApiResponse<ItemDto[]>` from `@hilo/shared`, then adds `normalizePagedItems` (handles array/items/data/data.data/data.items) + `resolvePagination` (guesses `totalItems` from the current page length — silently wrong cross-page). TypeScript can't catch it (everything optional), and the MR description frames it as a feature ("vá normalizePagedItems để support nhiều response shape từ BE") — the phrase "nhiều response shape" IS the red flag: the FE doesn't know the BE contract. Checks: (1) every `ApiResponse<...>` generic in `apis/` must be `ItemDto` or `ItemDto[]` — `data` is the payload itself; (2) grep the feature for wrapper types + response-shape helpers (`normalizePagedItems|resolvePagination|CrmPagedListResponse|normalizeApiCollectionData`); (3) shape mismatch → verify BE (Swagger `https://api-erp.vppos.vn/docs` / curl) and fix the TYPE, not the code. **Live-spec recipe (verified MR !549):** the Scalar docs page `https://api-erp.vppos.vn/docs` is HTML — `grep -o 'url="[^"]*"'` it to find the spec path (currently `/openapi.yaml`, ~1.4MB; `/openapi.json`, `/docs/openapi.yaml`, `/api/openapi.json` all return 405), then grep the YAML for the endpoint's enum/params (`customerType: ... description: Loại khách hàng (ENTERPRISE, HOUSEHOLD_BUSINESS, INDIVIDUAL)`). Canonical envelope: `docs/solutions/conventions/2026-08-05-api-response-envelope-contract.md`.
- **Spec-driven MRs: the linked issue IS the contract — verify against its ACs** (real case, MR !544 + issue #129): when the MR description cites an issue (`- **Issue / Ticket**: #N`), fetch it with `get_issue` BEFORE reading the diff. Spec-driven issues embed a `Contract bắt buộc` section — exact payloads (lock: `{organizationId, attendanceSheetId, lockScope, note, notification:false}`, NO `lockYear/lockMonth`), endpoint paths (`encodeURIComponent(attendanceSheetId)` in unlock, never `data.id`/period-lock UUID), response semantics (`resultType: 'locked'|'blocked_by_issues'`, unlock returns `ready|processing`), and acceptance criteria (target-only cache update, control sheet untouched, reason required after trim, disable while pending). - **Convention violation usually means the convention is INVISIBLE in the docs — fix the docs alongside the MR finding** (real case, MR !539 → docs MR !545): when an MR violates a documented convention, diagnose why agents keep missing it instead of blaming the author: (1) `git grep 'ApiResponse' AGENTS.md` → 0 hits = the contract TYPE is never named in the guide hierarchy, so agents can't reference it; (2) the guide's inline description may be stale/wrong — root AGENTS.md described the envelope as `{ data, success, code }`, but no `code` field exists (real: `{ success, data: T, error, meta }`), and a wrong field list erases the convention; (3) plan docs (`docs/plans/*.md`) are mandatory reading per AGENTS.md workflow → a plan doc citing the anti-pattern as canonical ("BE trả dạng này", 2026-08-03 plan blessed `CrmPagedListResponse`) actively propagates it — de-bless it in the same effort; (4) shared packages can legitimize the anti-pattern (`normalizeApiCollectionData` in `@hilo/shared` accepting `T[]|{items}|Record`). Output: flag the MR 🔴 AND ship a docs MR (AGENTS.md rule + `docs/solutions/conventions/` entry + plan-doc fix) so the next agent starts knowing. (3) `merge_merge_request` with `should_remove_source_branch` matching the MR's `force_remove_source_branch`. (4) verify post-merge: `git fetch origin <target-branch>` → tip shows `Merge branch '<source>' into '<target>'`; the source branch may linger on the remote for a while (GitLab deletes async — not an error).
- **Transition action targeting an optional nested id** (real case, MR !527) — a Confirm/Reject action resolves its target via `entity.sub?.id || entity.subId` where `sub` is optional in the DTO → rows without the sub-object call the API with `undefined` id. Even after status-gating actions, guard the id resolution too. Check every action's id source against the DTO's optionality.
- **URL state leaked across tabs sharing one schema** (real case, MR !527) — two tabs (receivables / payment-receipts) share `useReceivablesUrlState`; `setTab` resets only `page`, not `q`/filters. A search typed in tab A survives into tab B where `q` maps to a *different* param (customerId vs receivableId) → tab B opens on a confusing empty list. When tabs share URL state but map params differently, reset or namespace the state per tab.
- **Scope-creep path rename with stale nav** (real case, MR !527) — the MR renamed an unrelated feature's route constant (`FINANCE_INVOICE_REQUESTS` → `FINANCE_INVOICE_MANAGEMENT`, route now `/finance/invoice-management`) while `navigation.ts` kept the old feature path `/invoice-requests` → shell-built hrefs and old deep links land on the catch-all redirect. A route/path rename for a feature outside the MR's stated scope is scope creep AND a latent dead link; flag even when the module is `enabled: false` (hidden nav) — deep links/bookmarks still break.
- **Double-submit: aggregate `isMutating` computed but never threaded to the submit button** (real case, MR 512) — the crud hook computes `isMutating` (union of all `isPending`), but it isn't passed to the dialog's Save button, and the submit handler is unguarded → double-click fires two create/update mutations → duplicate records. When a hook derives an aggregate pending flag, verify it actually reaches the dialog submit `disabled`/`loading`.
- **Derived-readonly required field blocks the flow** (real case, MR 512) — a required input that's read-only and derived from a parent (product tax rate from the selected category) means a parent without that value makes the child impossible to create; validation referencing the derived string (`!createForm.taxRate`) silently blocks with a generic toast. Check that validation keys off a real user-input field (the id), not a derived display string, and that the readonly field has a fallback/override path.
- **Error-swallowing API layer → dead ErrorState** (real case, MR !512) — `apis/product-catalog.ts` wraps every exported function in try/catch and returns a fabricated `{success: false, data: null, error}` via `buildErrorResponse`/`parseApiError`. React Query then treats failures as SUCCESS: `query.isError` NEVER fires, the component's ErrorState+Retry branch (`ProductCatalogView.tsx:497`) is dead code, and `data?.data.x ?? []` renders a silent EMPTY table on backend failure — indistinguishable from a real empty dataset, no retry path. Detection: grep apis/ for `catch` + response-fabrication helpers; then check whether consumers rely on `isError` (dead branch) or manually check `response.success` (the tell that the layer swallows errors). Repo convention: dumb api functions do NOT catch — let it throw, React Query surfaces `isError`, components render ErrorState + `refetch`. Also symptomatic: hardcoded Vietnamese fallback messages inside apis/ ('Không thể tạo sản phẩm') instead of `getApiErrorDisplayMessage` from `@hilo/shared`. See `references/api-layer-convention-survey.md` for the full apis/ dimension checklist.
- **`git stash` in a shared worktree can silently DROP in-progress edits** (real incident, self-MR #95) — to test whether a failing spec was pre-existing on develop, ran `git stash && vitest && git stash pop` inside a worktree with uncommitted changes; after pop, `packages/shared/src/api/endpoints.ts` edits had VANISHED from src while `dist/` still had them (src/dist diverged, LSP went red). Recovery = re-apply the patch from memory/diff. **Never use `git stash` to test "pre-existing failure"** — compare against the base ref directly instead: `git show <base-sha>:<file>` (or `git diff <base-sha> -- <file>`) answers "was this failing before my change?" with zero risk. If a stash is unavoidable, verify `git status` + `git diff --stat` AFTER pop and re-apply anything missing before continuing.\n- **\"Is this issue actually done?\" — labels and state LIE** (real case, issue #95) — issue sat `opened` with labels `ready-for-agent` + `status::review`, assignee had been working for days, but ZERO code existed: no linked MR, no open MR containing the feature keyword, no branch, and none of the Files listed in the description existed on develop. Label `status::review` with no linked MR = \"moved the label, did no work\". Verification recipe (cheap, all parallel): (1) `git ls-tree -r origin/develop --name-only | grep -i <target-files>` — do the Files from the issue description exist on develop?; (2) `mcp__gitlab__list_merge_requests(project_id, search=<keyword>, state=opened)` — any open MR?; (3) `mcp__gitlab__list_issue_links` — any linked MR?; (4) `git branch -r | grep -i <keyword>` — any remote branch? - **Empty test file breaks vitest** (real case, self-MR #120) — deleting a test's CONTENT but leaving the file as 0B makes vitest fail the whole suite: `Error: No test suite found in file <path>` → `Test Files 1 failed | 3 passed`. - **Shared-component adoption breaks unrelated tests — matchMedia & Router traps** (real case, MR !531 employee): adding `TableFiltersPanel` to a component makes EVERY test that renders it crash with `TypeError: window.matchMedia is not a function` (`TableFiltersPanel` → `ResponsiveModal` → `useMediaQuery`; jsdom lacks matchMedia). ## Anti-Patterns

| Don't | Do instead |
|-------|------------|
| Only read the diff for UI migrations | Read the shared component's source code to verify compatibility |
| Check i18n in only one language | Always check both `en/` and `vi/` |
| Read local `develop` instead of the MR branch | Read every file via `get_file_contents(ref=<branch>)` |
| Assume removed imports are unused | Verify the import isn't used elsewhere in the file first |
| Approve wrapper interfaces around `ApiResponse` + normalize/resolve helpers for BE response shapes | Type `ApiResponse<T>` with T = item\|item[] (data IS the payload, pagination in `meta.pagination`); verify BE contract (Swagger/curl) and fix the TYPE, not the code |
